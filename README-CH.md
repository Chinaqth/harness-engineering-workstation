# Harness Engineering 工作基站

一个可以从个人实践起步，并逐步扩展到大型组织治理流程的 AI 工程控制平面。

[English README](README.md)

## 项目概括

这个仓库是团队与 Coding Agent 协作方式的系统记录。它通过 Git 管理工程规则、交付流程、决策边界、可复用 Skill、评估契约、验证证据和演进历史，把模型能力转化为稳定、可治理的工程能力。

工作基站不绑定具体模型、IDE 或供应商，也不追求编写一个“万能提示词”。它关注模型周围的完整工作环境，让 AI 工作具备以下特征：

- 目标、范围和上下文可以被发现；
- 权限和执行深度与风险匹配；
- 工作可以跨会话、跨人员继续；
- 系统行为可以被观察；
- 完成结论有独立、可复现的证据；
- 错误出现后能够回滚、恢复或升级；
- 每次交付都能沉淀为组织知识。

### 这个仓库是什么

- AI 辅助工程的组织级控制平面；
- 规则、红线、模板、Skill 和评估标准的版本化来源；
- 以制品为核心的 `3+1` 交付闭环参考实现；
- 企业项目逐步采纳 Harness Engineering 的起点。

### 这个仓库不是什么

- 不替代产品需求、业务架构、测试体系和人的最终责任；
- 不是通用提示词集合；
- 不是生产部署系统；
- 不是给 Agent 授予长期或无限权限的理由；
- 不能在没有真实项目证据时直接证明企业已经具备成熟能力。

## 为什么需要 Harness Engineering

Prompt Engineering 优化一次指令，Context Engineering 优化模型当前能看到什么，而 Harness Engineering 管理完整执行闭环：

```text
业务意图
  -> 选择上下文
  -> 评估风险
  -> 计划并建立契约
  -> 在预算内生成
  -> 观察系统行为
  -> 独立评估
  -> 批准、恢复或升级
  -> 将证据沉淀为组织知识
```

优化对象不再是模型的一次回答，而是整个“人、Agent、工具、规则和系统”共同组成的工作流可靠性。

## 工程思想

### 1. 仓库是持久记忆

聊天记录是临时界面。需求、决策、进度、证据和经验必须进入 Git 管理的制品，让另一个合格的执行者可以检查并继续工作。

### 2. 渐进式上下文优于超长指令

`AGENTS.md` 只承担导航职责。Agent 根据当前任务按需读取架构、治理、工作流、变更记录和深层参考资料。

### 3. 自治是一组风险预算

Agent 的权限应受到范围、工具、权限、外部副作用、时间、成本、证据和升级条件约束。风险越高，检查点越密集，职责分离越严格。

### 4. 验收必须可以执行

重要目标应拥有稳定的验收编号、机器可读状态、可复现检查和证据路径。不能因为输出看起来完整或 Agent 表示有信心就判定完成。

### 5. 生成和评估是不同职责

Generator 负责实现并提供证据；Evaluator 负责挑战证据。对于 G2/G3 工作，最终技术判定属于 Evaluator。`blocked` 不能被当作通过。

### 6. 可观测性是 Agent 的输入能力

健康检查、日志、链路、截图、结构化事件和可重复的用户旅程都属于 Agent 接口。无法观察的行为无法被可靠评估。

### 7. 每次交付都应改善工作基站

重复出现的问题应转化为规则、检查、测试、Skill 或架构指导。一次任务不仅要交付结果，还要降低下一次同类任务的不确定性。

## 运行模型

项目采用 `3+1` 生命周期：

| 阶段 | 目的 | 主要输出 |
| --- | --- | --- |
| 1. 计划 | 澄清意图、范围、风险、标准和权限 | 需求、任务、决策、自治预算 |
| 2. 实现 | 执行最小、可逆、已批准的工作单元 | 代码或文档、进度、验证证据 |
| 3. 评估与交付 | 重现关键行为并给出结论 | 验收状态、问题、回滚指导 |
| +1. 组织化沉淀 | 保存经验并改善未来工作 | 归档记录、规则、Skill、测试、指标 |

```text
Owner 提出意图
    |
Planner -> 需求 + 验收 + 契约
    |
Generator -> 实现 + 进度 + 证据
    |
Evaluator -> pass / fail / blocked
    |
Owner 批准 -> 交付或升级
    |
Archiver -> 持久知识和下一轮系统改进
```

详细规则参见 [3+1 工作流](workflows/3-plus-1.md)。

## 风险与自治等级

| 等级 | 典型工作 | 默认控制方式 |
| --- | --- | --- |
| G0 — 本地且可逆 | 文档、测试、安全重构 | Agent 可以本地执行和验证 |
| G1 — 有限影响 | 新依赖、公共接口、小型迁移 | 记录理由并接受人工评审 |
| G2 — 高影响 | 权限、安全边界、破坏性兼容变更 | 完整变更制品、独立评估、批准和回滚演练 |
| G3 — 不可逆或受监管 | 生产数据删除、敏感信息披露、重大合规变更 | 人主导执行、双人批准、审计记录 |

风险由影响范围、可逆性、数据敏感度和外部副作用共同决定。存在不确定性时向上取整。完整自治预算见 [AUTONOMY_POLICY.md](docs/AUTONOMY_POLICY.md)。

## 变更制品

完整的 G2/G3 变更包含：

```text
changes/<YYYYMMDD-short-name>/
├── requirements.md   # 原因、范围、风险、验收、预算、回滚
├── task.md           # 执行计划、验证矩阵、最终判定
├── acceptance.json   # 稳定验收项、状态、证据
├── progress.md       # 当前状态和恢复点
├── contract.md       # Generator–Evaluator 契约
└── decision.md       # 决策取舍和后果
```

G0 可以记录在任务或 Pull Request 中。G1 需要 `requirements.md`、`task.md` 和 `progress.md`。风险越高，制品越完整。

## 快速开始

1. 阅读 [AGENTS.md](AGENTS.md)、[CORE.md](rules/CORE.md) 和当前项目上下文。
2. 将任务评估为 G0–G3。
3. 对于 G1 及以上任务，将 `changes/_template/` 复制到带日期的变更目录，并根据风险保留必要制品。
4. 在实现前定义可观察的验收标准。
5. 声明自治预算和人工审批点。
6. 每次只实现一个受控工作单元，并持续更新 `progress.md`。
7. 运行：

   ```bash
   ./scripts/harness-check.sh
   ```

8. 对重要的用户可见行为使用 `skills/end-to-end-evaluator`。
9. 记录最终判定、剩余风险和回滚方式。
10. 归档变更，并将稳定结论升级为规则、Skill、测试或架构知识。

## 多场景用例流程

下面的用例重点说明项目文件在真实工作中如何协作。表格使用五种文件操作：

- **读取：** 加载约束、规则或上下文；
- **创建：** 在执行前建立持久记录；
- **更新：** 持续外化进度、状态和证据；
- **验证：** 运行确定性检查或独立评估；
- **归档：** 保存完整记录，并将稳定结论升级为长期知识。

所有场景共享一条基础文件流：

```text
AGENTS.md
  -> docs/ + rules/
  -> changes/<change-id>/
  -> 具体实现和项目测试
  -> scripts/ + skills/
  -> Pull Request 和 CI
  -> changes/archive/ + 长期规则更新
```

风险等级决定其中哪些文件和阶段是强制的。

### 场景 A：修正 README 中的拼写错误 — G0

这个变更只影响本地文档，可以立即撤销，也不会改变公共契约。

| 阶段 | 工作流如何运行 | 涉及的文件与操作 |
| --- | --- | --- |
| 进入 | Agent 加载仓库语言规范和完成标准 | **读取** `AGENTS.md` 和 `rules/CORE.md` |
| 定界 | 在任务或 Pull Request 中记录目标、验收和 G0 风险；不需要创建变更目录 | **使用** `.github/pull_request_template.md` |
| 实现 | 只编辑受到影响的文档 | **更新** `README.md` 或其他目标文档 |
| 验证 | 检查必需文件、语言策略、链接和验证器测试 | 使用 `scripts/harness-check.sh` **验证** |
| 交付 | 在交付记录中写明差异、检查结果和回滚方式 | **更新** Pull Request 描述 |
| 沉淀 | 除非错误暴露了反复出现的文档问题，否则不升级长期规则 | 必要时**更新** `rules/CORE.md` 或文档检查器 |

如果文档修改改变了政策、公共接口、审批边界或组织级规范，流程必须升级到 G1 或更高等级。

### 场景 B：增加依赖或公共 API — G1

示例：产品仓库增加一个第三方库，同时新增一个 API 响应字段。

| 阶段 | 工作流如何运行 | 涉及的文件与操作 |
| --- | --- | --- |
| 进入 | Agent 发现项目约定和风险规则 | **读取** `AGENTS.md`、`docs/GOVERNANCE.md` 和 `docs/AUTONOMY_POLICY.md` |
| 计划 | Planner 记录必要性、替代方案、兼容性、验收和回滚 | **创建** `changes/<id>/requirements.md` |
| 拆分 | 将工作拆成依赖审查、实现、兼容性测试和文档更新 | **创建** `changes/<id>/task.md` |
| 建立连续性 | 记录初始版本、环境、未完成工作和恢复点 | **创建并持续更新** `changes/<id>/progress.md` |
| 实现 | Generator 修改产品文件，并逐项完成受控任务单元 | **更新** 产品代码、测试、`task.md` 和 `progress.md` |
| 验证 | 验证矩阵把每条标准映射到构建、测试、兼容性或安全证据 | **更新** `task.md`；运行产品检查和 `scripts/harness-check.sh` |
| 评审 | 人工在合并前检查决策理由、兼容性、证据和回滚 | **使用** `.github/pull_request_template.md` 和 CI |
| 收口 | 记录最终结果与剩余风险，并从活动上下文中移出 | **归档**到 `changes/archive/<year>/<id>/` |

当依赖选择或接口设计包含重要取舍时，应增加 `decision.md`。G1 默认不要求完整的六项制品。

### 场景 C：修改权限或安全边界 — G2

示例：应用修改“哪些角色可以导出客户记录”。

| 阶段 | 工作流如何运行 | 涉及的文件与操作 |
| --- | --- | --- |
| 风险分类 | 数据敏感度、权限扩大、外部副作用和可逆性共同确定 G2 | **读取** `docs/GOVERNANCE.md`、`docs/AUTONOMY_POLICY.md` 和 `rules/CORE.md` |
| 定义范围 | Owner 和 Planner 固定范围、非目标、验收、自治预算和回滚 | 从模板**创建** `requirements.md` |
| 让状态可执行 | 稳定的验收编号以 `pending` 开始，不能为了迁就实现结果而改写描述 | **创建** `acceptance.json` |
| 分离职责 | 在实现前确定关键用户旅程、证据质量、Generator 边界和 Evaluator 判定权 | **创建** `contract.md` |
| 记录取舍 | 保存备选方案、安全影响和重新评估条件 | **创建** `decision.md` |
| 执行 | Generator 每次只完成一个已批准、可回滚的任务，并记录版本、环境、证据和下一步 | **更新** `task.md`、`progress.md`、产品代码和测试 |
| 观察系统 | 通过稳定适配器启动、执行、观察、重置并停止系统 | **遵循** `docs/OBSERVABILITY.md` |
| 独立评估 | Evaluator 独立重现有权限和无权限用户旅程，并核对每个关键验收项 | **使用** `skills/end-to-end-evaluator/`；**更新** `acceptance.json` 和 `task.md` 判定 |
| 强制检查 | 变更语义、工作基站完整性和产品检查全部通过 | 使用 `scripts/validate_change.py`、`scripts/harness-check.sh`、产品测试和 CI **验证** |
| 批准和收口 | Owner 在合并或修改权限前审查独立判定和回滚证据 | **使用** Pull Request；之后**归档**完整六项制品 |

如果评估因权限或可观测性不足而被阻塞，`acceptance.json` 必须保持 `blocked`。缺少证据不能转化为批准。

### 场景 D：受监管的生产数据删除 — G3

仓库负责计划、约束和证据，真正不可逆的操作仍由人执行。

| 阶段 | 工作流如何运行 | 涉及的文件与操作 |
| --- | --- | --- |
| 建立授权 | 记录精确数据范围、法律依据、审批人、保留要求和禁止动作 | **创建**完整变更记录；**读取** `docs/GOVERNANCE.md` |
| 限制 Agent | AI 可以检查、模拟、起草和验证，但不能执行删除 | 在 `requirements.md` **记录** G3 预算，在 `contract.md` 记录停止条件 |
| 准备 | 记录 Dry Run、数据数量、备份或恢复条件和预期最终状态 | **更新** `task.md`、`progress.md` 和 `acceptance.json` 证据路径 |
| 正式批准 | 两名授权人员在 Generator 角色之外批准固定目标和执行窗口 | 在 `decision.md` 和交付记录中**记录**批准引用 |
| 执行 | 由获得授权的人执行状态变更 | 不得把不可逆动作委托给 Skill 或 Generator |
| 确认 | 独立 Evaluator 检查最终状态、审计证据和恢复义务 | **更新** `acceptance.json` 和 `task.md` 中的 pass、fail 或 blocked |
| 留存 | 按治理要求保存完整决策和证据记录 | **归档**变更并保留外部审计引用 |

工作基站不会把缺少授权解释成默认授权。

### 场景 E：跨多个会话持续开发一个功能

这个场景说明当任务持续时间超过一次聊天上下文时，同一组文件如何传递状态。

| 时间点 | 文件如何运作 |
| --- | --- |
| 第一次会话开始 | **读取** `requirements.md` 和 `contract.md`；从 `task.md` 选择下一个未完成任务 |
| 开始执行 | 在 `progress.md` **更新**当前版本、环境、阶段和基线 |
| 验证某个验收项 | 将证据写入 `acceptance.json` 对应编号，不能修改验收描述 |
| 完成一个任务单元 | 勾选 `task.md` 中的任务和验证矩阵，并刷新 `progress.md` |
| 会话暂停 | 在 `progress.md` 记录已完成内容、阻塞项、剩余风险和精确的下一个命令或文件 |
| 后续会话恢复 | **读取**仓库状态和 `progress.md`，编辑前先确认记录的版本 |
| 范围或风险变化 | 停止实现，经 Owner 批准后**更新** `requirements.md`、`decision.md` 和 `contract.md` |
| 完整用户旅程通过 | Evaluator 核对 `acceptance.json`，随后归档记录 |

Git 保存代码版本，`progress.md` 保存执行状态，`acceptance.json` 保存结果状态。聊天摘要不能替代这三类权威状态。

### 场景 F：诊断并修复接近生产环境的缺陷

示例：用户可以提交订单，但页面始终没有显示确认结果。

| 阶段 | 工作流如何运行 | 涉及的文件与操作 |
| --- | --- | --- |
| 定位 | Agent 加载项目命令、约束和评估要求 | **读取** `AGENTS.md`、`rules/CORE.md` 和相关架构 |
| 记录问题 | 按风险等级记录症状、影响、非目标和可观察的恢复标准 | 在 `changes/<id>/` 下**创建** G1 或 G2 制品 |
| 重现 | 使用与真实用户相同的旅程观察故障 | **遵循** `docs/OBSERVABILITY.md`；把日志、链路、截图或测试输出加入证据 |
| 计划修复 | 拆分被破坏的不变量、最小修复、回归覆盖和回滚 | **更新** `task.md` 和 `progress.md` |
| 实现修复 | Generator 只修改最小受支持范围，并增加先失败后通过的回归测试 | **更新**产品代码和测试 |
| 独立评估 | 重新运行原始用户旅程和相关负向路径 | **使用** `skills/end-to-end-evaluator/`；**更新**判定和验收证据 |
| 组织化沉淀 | 重复故障升级为确定性测试、规则、审计检查、架构说明或 Skill 流程 | **更新** `rules/`、`scripts/`、`docs/` 或 `skills/` |
| 收口 | 检查通过、剩余风险记录完成后归档 | 使用项目检查和 `scripts/harness-check.sh` **验证**；随后**归档** |

如果用户只授权诊断，流程应在报告有证据的原因后停止，不能自动进入修复阶段。

### 场景 G：修改工作基站规则或创建 Skill

这个场景展示控制平面如何更新自身。

| 阶段 | 工作流如何运行 | 涉及的文件与操作 |
| --- | --- | --- |
| 识别问题 | 重复评审意见或重复失败说明缺少长期指导 | **读取**历史归档、审计结果和 `docs/knowledge/` |
| 纳入治理 | 由于可能改变组织规则或审批边界，按 G2 处理 | **读取** `docs/GOVERNANCE.md`；**创建**完整六项变更制品 |
| 选择机制 | 强制不变量变成规则或检查；可复用专业流程变成 Skill | 在 `decision.md` 中**记录**选择理由 |
| 实现 | 规则写入 `rules/`；确定性执行写入 `scripts/`；工作流写入 `skills/<name>/` | **创建或更新**对应控制平面文件 |
| 验证 | 规则变更通过完整 Harness 检查；Skill 通过结构验证和真实触发测试 | 运行 `scripts/harness-check.sh`；**更新** `task.md` 和 `acceptance.json` |
| 独立评估 | Evaluator 检查规则冲突、红线削弱、触发条件不清和迁移影响 | 根据场景**使用** `skills/harness-audit/` 或 `skills/end-to-end-evaluator/` |
| 发布 | 入口文档和路由表能够找到新的长期能力 | 仅在需要时**更新** `AGENTS.md`、README、架构、治理或审计量表 |
| 沉淀 | 完成的提案和证据成为系统演进历史 | **归档**变更，并通过知识维护流程持续检查 |

这样可以避免控制平面不断累积无法被发现、无法执行的孤立指令。

### 场景 H：在现有产品仓库中采纳工作基站

控制平面文件用于审计和指导采纳；具体产品事实仍保留在产品仓库中。

| 阶段 | 工作流如何运行 | 涉及的文件与操作 |
| --- | --- | --- |
| 建立基线 | 根据证据评估上下文、工具、编排、记忆、评估、护栏和治理 | **使用** `skills/harness-audit/` 及其量表 |
| 规划采纳 | 按风险排列差距，并转换为边界清楚的采纳标准 | 在产品仓库中**创建**变更记录 |
| 增加入口 | 产品增加简洁入口，指向自己的架构、命令和领域事实 | **创建或更新**产品项目的 `AGENTS.md` |
| 增加控制 | 继承组织红线和风险处理，同时保留更具体的项目规则 | **引用** `rules/CORE.md`、治理和自治政策 |
| 增加可见性 | 产品实现 start、ready、exercise、observe、reset 和 stop 接口 | 按照 `docs/OBSERVABILITY.md` **实现** |
| 试点 | 用一个 G1 和一个 G2 变更检验计划、交接、评估、批准和归档 | **使用**变更模板与 Evaluator Skill |
| 度量 | 记录返工、逃逸缺陷、交付时间、检查可靠性和例外到期情况 | **更新**产品项目的指标和决策记录 |
| 升级 | 明确评审并采纳新的控制平面版本 | **记录**版本和偏差；不得静默覆盖产品政策 |

## 企业落地路径

建议渐进式采纳：

| 阶段 | 重点 | 进展证据 |
| --- | --- | --- |
| 1. 建立基线 | 入口、红线、变更模板、确定性检查 | 重要工作可见且可以复现 |
| 2. 建立治理 | 风险、Owner、审批、回滚、Skill 责任 | 高风险工作可以追踪 |
| 3. 建立度量 | 质量、周期、成本、返工、例外、评估可靠性 | 决策开始使用趋势数据 |
| 4. 自适应改进 | 动态上下文、工具选择、评估集、知识自动升级 | Harness 变更能改善真实指标 |

不要用提示词数量或生成代码行数评价个人。应衡量系统是否减少缺陷、歧义、返工、不安全操作和恢复成本。

## 项目验证

运行完整检查：

```bash
./scripts/harness-check.sh
```

它会验证必要文件、可疑凭据文件名、语言策略、变更记录语义、文档链接、活动变更新鲜度和检查器测试。

## 当前状态与下一步

当前基线为 `v0.2`。它已经建立 L2 治理所需的控制平面接口，但真正的企业就绪仍需要真实产品项目的采纳证据。

建议下一步选择一个正在开发的仓库进行试点：

- 一个 G1 功能或依赖变更；
- 一个 G2 安全、权限或兼容性变更；
- 一套项目专属可观测性适配器；
- 一段用于衡量返工、缺陷、交付时间和评估可靠性的观察周期。

设计依据可继续阅读 [成熟度模型](docs/MATURITY_MODEL.md) 和 [视频分析文档](docs/knowledge/harness-engineering-video-analysis-bv12lr1b3eut.md)。
