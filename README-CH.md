# Harness Engineering 工作基站

一个可以从个人实践起步，并逐步扩展到大型组织治理流程的 AI 工程控制平面。

[English README](README.md)

## 项目概括

这个仓库是团队与 Coding Agent 协作方式的系统记录。它通过 Git 管理工程规则、交付流程、决策边界、可复用 Skill、评估契约、验证证据和演进历史，把模型能力转化为稳定、可治理的工程能力。

工作基站不绑定具体模型、IDE 或供应商，也不追求编写一个“万能提示词”。它关注模型周围的完整工作环境，让 AI 工作具备以下特征：

- 目标、范围和上下文可以被发现；
- 权限和执行深度与风险匹配；
- 工作可以跨会话、跨人员继续；
- 系统行为可以被观察；
- 完成结论有独立、可复现的证据；
- 错误出现后能够回滚、恢复或升级；
- 每次交付都能沉淀为组织知识。

### 这个仓库是什么

- AI 辅助工程的组织级控制平面；
- 规则、红线、模板、Skill 和评估标准的版本化来源；
- 以制品为核心的 `3+1` 交付闭环参考实现；
- 企业项目逐步采纳 Harness Engineering 的起点。

### 这个仓库不是什么

- 不替代产品需求、业务架构、测试体系和人的最终责任；
- 不是通用提示词集合；
- 不是生产部署系统；
- 不是给 Agent 授予长期或无限权限的理由；
- 不能在没有真实项目证据时直接证明企业已经具备成熟能力。

## 底座、Domain Pack 与具体项目

企业接入采用三个相互独立、可版本化的作用域：

| 作用域 | 权威来源 | 职责 |
| --- | --- | --- |
| Harness 底座 | 当前仓库 | 跨职能工作流、风险、授权、路由协议、任务状态、证据和治理 |
| Domain Pack | 独立私有仓库 `harness-engineering-domain-packs` | 可复用的职能路由、能力、流程、规则、Skill、工具和评估器 |
| 具体产品项目 | 各产品仓库 | 架构、命令、启用的 Pack 版本、本地负责人、约束和任务记录 |

当前版本只定义路由协议和验证契约，并没有交付生产级 Router。未来符合协议的 Resolver 会先把自然语言任务整理为 Task Envelope，选择且只选择一个已注册的 Kernel 任务工作流，评估影响与风险，再结合不可变的 Domain 注册表版本和项目 Overlay 解析可用专业能力，最后输出可追溯的 Routing Plan。只有被选中的专业内容才会被加载；缺失能力、输入、冲突和结构化审批门必须保留为明确状态。具体功能和 Bug 症状属于任务上下文，不能被包装成任务特有的 Skill。

详细说明见 [企业 Domain 架构](docs/ENTERPRISE_DOMAIN_ARCHITECTURE.md) 与 [任务到能力的路由协议](docs/ROUTING.md)。

## 为什么需要 Harness Engineering

Prompt Engineering 优化一次指令，Context Engineering 优化模型当前能看到什么，而 Harness Engineering 管理完整执行闭环：

```text
业务意图
  -> 选择上下文
  -> 评估风险
  -> 计划并建立契约
  -> 在预算内生成
  -> 观察系统行为
  -> 独立评估
  -> 批准、恢复或升级
  -> 将证据沉淀为组织知识
```

优化对象不再是模型的一次回答，而是整个“人、Agent、工具、规则和系统”共同组成的工作流可靠性。

## 工程思想

### 1. 仓库是持久记忆

聊天记录是临时界面。需求、决策、进度、证据和经验必须进入 Git 管理的制品，让另一个合格的执行者可以检查并继续工作。

### 2. 渐进式上下文优于超长指令

`AGENTS.md` 只承担导航职责。Agent 根据当前任务按需读取架构、治理、工作流、变更记录和深层参考资料。

### 3. 自治是一组风险预算

Agent 的权限应受到范围、工具、权限、外部副作用、时间、成本、证据和升级条件约束。风险越高，检查点越密集，职责分离越严格。

### 4. 验收必须可以执行

重要目标应拥有稳定的验收编号、机器可读状态、可复现检查和证据路径。不能因为输出看起来完整或 Agent 表示有信心就判定完成。

### 5. 生成和评估是不同职责

Generator 负责实现并提供证据；Evaluator 负责挑战证据。对于 G2/G3 工作，最终技术判定属于 Evaluator。`blocked` 不能被当作通过。

### 6. 可观测性是 Agent 的输入能力

健康检查、日志、链路、截图、结构化事件和可重复的用户旅程都属于 Agent 接口。无法观察的行为无法被可靠评估。

### 7. 每次交付都应改善工作基站

重复出现的问题应转化为规则、检查、测试、Skill 或架构指导。一次任务不仅要交付结果，还要降低下一次同类任务的不确定性。

## 运行模型

项目采用 `3+1` 生命周期：

| 阶段 | 目的 | 主要输出 |
| --- | --- | --- |
| 1. 计划 | 澄清意图、范围、风险、标准和权限 | 需求、任务、决策、自治预算 |
| 2. 实现 | 执行最小、可逆、已批准的工作单元 | 代码或文档、进度、验证证据 |
| 3. 评估与交付 | 重现关键行为并给出结论 | 验收状态、问题、回滚指导 |
| +1. 组织化沉淀 | 保存经验并改善未来工作 | 归档记录、规则、Skill、测试、指标 |

```text
Owner 提出意图
    |
Planner -> 需求 + 验收 + 契约
    |
Generator -> 实现 + 进度 + 证据
    |
Evaluator -> pass / fail / blocked
    |
Owner 批准 -> 交付或升级
    |
Archiver -> 持久知识和下一轮系统改进
```

详细规则参见 [3+1 工作流](workflows/3-plus-1.md)。

## 风险与自治等级

| 等级 | 典型工作 | 默认控制方式 |
| --- | --- | --- |
| G0 — 本地且可逆 | 文档、测试、安全重构 | Agent 可以本地执行和验证 |
| G1 — 有限影响 | 新依赖、公共接口、小型迁移 | 记录理由并接受人工评审 |
| G2 — 高影响 | 权限、安全边界、破坏性兼容变更 | 完整变更制品、独立评估、批准和回滚演练 |
| G3 — 不可逆或受监管 | 生产数据删除、敏感信息披露、重大合规变更 | 人主导执行、双人批准、审计记录 |

风险由影响范围、可逆性、数据敏感度和外部副作用共同决定。存在不确定性时向上取整。完整自治预算见 [AUTONOMY_POLICY.md](docs/AUTONOMY_POLICY.md)。

## 变更制品

完整的 G2/G3 变更包含：

```text
changes/<YYYYMMDD-short-name>/
├── requirements.md   # 原因、范围、风险、验收、预算、回滚
├── task.md           # 执行计划、验证矩阵、最终判定
├── acceptance.json   # 稳定验收项、状态、证据
├── progress.md       # 当前状态和恢复点
├── contract.md       # Generator–Evaluator 契约
└── decision.md       # 决策取舍和后果
```

G0 可以记录在任务或 Pull Request 中。G1 需要 `requirements.md`、`task.md` 和 `progress.md`。风险越高，制品越完整。

## 快速开始

1. 阅读 [AGENTS.md](AGENTS.md)、[CORE.md](rules/CORE.md) 和当前项目上下文。
2. 将具体任务事实整理为 Task Envelope，并选择一个已注册的 Kernel 任务工作流。
3. 将任务评估为 G0–G3，再通过项目 Overlay 解析启用的 Domain 能力及其声明的通用 Skill。
4. 对于 G1 及以上任务，将 `changes/_template/` 复制到带日期的变更目录，并根据风险保留必要制品。
5. 在实现前定义可观察的验收标准。
6. 声明自治预算和绑定明确范围的人工审批门；由通用 Domain Skill 贡献专业评估及目标项目的具体 `task.md`。
7. 对 Domain 增强的修改性任务，向用户完整展示当前 `task.md` 并暂停；把内容摘要绑定到审批，只有用户明确确认后才能恢复，用户要求修改时必须重新完整展示。
8. 仅在必要审批门通过后实现受控工作单元，并持续更新 `progress.md`。
9. 运行：

   ```bash
   ./scripts/harness-check.sh
   ```

10. 对重要的用户可见行为使用 `skills/end-to-end-evaluator`。
11. 记录最终判定、剩余风险和回滚方式。
11. 归档变更：跨职能结论进入底座，专业实践进入 Domain Pack，项目事实留在具体项目。

## 多场景用例流程

下面的用例重点说明项目文件在真实工作中如何协作。表格使用五种文件操作：

- **读取：** 加载约束、规则或上下文；
- **创建：** 在执行前建立持久记录；
- **更新：** 持续外化进度、状态和证据；
- **验证：** 运行确定性检查或独立评估；
- **归档：** 保存完整记录，并将稳定结论升级为长期知识。

所有场景共享一条基础文件流：

```text
AGENTS.md
  -> docs/ + rules/
  -> Task Envelope + 任务工作流注册表
  -> Domain 注册表 + 项目 Overlay
  -> Routing Plan + 被选中的 Domain Pack 内容
  -> changes/<change-id>/
  -> 具体实现和项目测试
  -> scripts/ + skills/
  -> Pull Request 和 CI
  -> changes/archive/ + 长期规则更新
```

用户通过真实生产目标进入系统，而不是先选择治理等级。工作基站在内部评估影响和可逆性，再决定需要使用多完整的变更制品。

不同生产场景中的 Domain 路由体现也不同：

| 生产请求 | 典型路由方式 | 涉及的文件 |
| --- | --- | --- |
| 开发一个新应用 | Product 和 Design 先明确问题；当架构和交付范围具体化后，再加入平台、Security、QA 与 Operations 能力 | Task Envelope、Domain 注册表、项目 Overlay、Routing Plan，以及被选中的 Pack 工作流和评估器 |
| 实现一个功能点 | 现有项目特征先缩小平台能力范围；只有功能跨越边界时才加入安全、数据、无障碍或 QA 能力 | 项目 Overlay、路由元数据、能力依赖、被选中的 Skill 和工具 |
| 修改一个 Bug | 代码归属 Domain 主导诊断；原行为对应的评估器和受影响的边界 Domain 验证修复 | Task Envelope、诊断流程、项目可观测能力、Domain 评估器 |
| 不改变行为地重构 | 代码归属 Domain 主导实现，兼容性与架构评估器保护外部契约 | 能力契约、项目架构、兼容性评估器、验收证据 |
| 处理线上事故 | Operations 或 Reliability 能力负责协调，再将调查和修复路由给受影响的开发与安全 Domain | 高风险任务契约、审批门、事故流程、多 Domain Routing Plan |

### 场景 A：从零开发一个新应用

示例：把一个想法开发成可以真实使用的客户支持 Web 应用首个版本。

| 阶段 | 工作流如何运行 | 涉及的文件与操作 |
| --- | --- | --- |
| 发现上下文 | Agent 加载全局规则、已有产品信息、技术约束和完成标准 | **读取** `AGENTS.md`、`rules/CORE.md` 和相关 `docs/` |
| 定义产品 | 固定目标用户、核心问题、首版范围、非目标、约束和可观察的成功标准 | **创建** `changes/<id>/requirements.md` |
| 选择架构 | 保存技术栈、数据、集成、部署和重要取舍 | **创建** `decision.md`；**更新**产品架构 |
| 建立路线图 | 将应用拆成应用骨架、身份、首个用户旅程、数据持久化和发布等端到端增量 | **创建并更新** `task.md` |
| 定义完成条件 | 为用户可见旅程建立稳定验收编号和证据要求 | **创建** `acceptance.json` 和 `contract.md` |
| 增量开发 | 每次会话完成一个可用切片，并记录版本、环境、证据、阻塞项和下一步 | **更新**应用代码、测试、`task.md` 和 `progress.md` |
| 评估应用 | Evaluator 启动应用、执行关键旅程、观察失败并核对验收状态 | **遵循** `docs/OBSERVABILITY.md`；**使用** `skills/end-to-end-evaluator/` |
| 交付与沉淀 | 完成 CI、评审、回滚和剩余风险，将稳定经验写入项目知识 | **使用** Pull Request 和 CI；**归档**变更；必要时**更新**架构、规则或 Skill |

最终结果不是“生成了一批文件”，而是一个可以运行、且关键用户旅程有证据证明的应用。

### 场景 B：在现有应用中实现一个功能点

示例：为已有的数据分析产品增加“保存搜索条件”和通知功能。

| 阶段 | 工作流如何运行 | 涉及的文件与操作 |
| --- | --- | --- |
| 理解现有系统 | Agent 查找当前用户旅程、代码归属、接口、测试和架构约束 | **读取** `AGENTS.md`、产品架构、现有测试和相关历史变更 |
| 说明功能行为 | Planner 定义谁需要这个功能、什么发生变化、什么必须保持不变以及用户如何证明它有效 | **创建** `requirements.md` |
| 评估影响 | 根据数据、权限、兼容性、外部副作用和可逆性决定变更制品深度 | **读取**治理和自治政策；必要时**创建** `decision.md` |
| 纵向拆分 | 按可交付切片拆分数据模型、服务行为、界面、通知、测试和文档 | **创建并更新** `task.md` |
| 维持连续性 | 持续外化当前版本、环境、已完成切片、阻塞项和恢复点 | **创建并更新** `progress.md` |
| 实现 | Generator 修改最小受支持范围，并补充单元、集成和用户旅程测试 | **更新**产品代码、测试、`task.md` 和证据 |
| 评估 | 独立重现关键正向和负向旅程；影响较大的工作使用明确验收状态 | 根据影响**使用** `acceptance.json`、`contract.md` 和 `skills/end-to-end-evaluator/` |
| 发布 | 合并前核对 CI、人工评审、兼容性、文档、剩余风险和回滚 | **使用** `.github/pull_request_template.md`；**归档**完成记录 |

功能完成意味着它能在现有系统中正确工作，同时没有静默破坏相邻行为。

### 场景 C：诊断并修复一个 Bug

示例：用户可以提交订单，但确认页面始终没有出现。

| 阶段 | 工作流如何运行 | 涉及的文件与操作 |
| --- | --- | --- |
| 定位上下文 | Agent 加载项目命令、架构、近期变更、已知故障模式和当前授权范围 | **读取** `AGENTS.md`、相关 `docs/`、历史归档和 `rules/CORE.md` |
| 记录症状 | 保存预期行为、实际行为、受影响用户、发生频率、环境和非目标 | 在 `changes/<id>/` 下**创建**与影响匹配的制品 |
| 修改前重现 | 通过真实用户旅程观察故障，并保存日志、链路、截图或失败测试 | **遵循** `docs/OBSERVABILITY.md`；**更新** `progress.md` 和证据 |
| 隔离原因 | 将被破坏的不变量和最小可信修复写入工作计划 | **更新** `task.md`；只有重要取舍才增加 `decision.md` |
| 实现修复 | Generator 只修改最小范围，并增加一个修复前失败、修复后通过的回归测试 | **更新**产品代码、测试、`task.md` 和 `progress.md` |
| 重新评估 | 独立重跑原始旅程、相邻行为、边界条件和相关负向路径 | **使用** `skills/end-to-end-evaluator/`；**更新**验收证据和判定 |
| 防止复发 | 重复 Bug 类型转化为测试、确定性检查、规则、架构说明或 Skill 流程 | **更新** `tests/`、`scripts/`、`rules/`、`docs/` 或 `skills/` |
| 收口 | 检查通过，剩余风险和回滚记录完成，证据得到保留 | 运行产品检查和 `scripts/harness-check.sh`；**归档**变更 |

如果任务只授权诊断，流程应在报告有证据支持的原因后停止。

### 场景 D：在不改变行为的情况下重构模块

示例：将过大的计费服务拆成更小的组件，同时保持所有公共契约不变。

| 阶段 | 工作流如何运行 | 涉及的文件与操作 |
| --- | --- | --- |
| 建立不变量 | 声明公共 API、输出、副作用、性能预期以及不在本次处理范围内的清理工作 | **创建** `requirements.md`；**读取**架构和兼容性规则 |
| 保存基线 | 通过现有测试和代表性用户旅程记录结构变化前的行为 | 在 `task.md` 中**更新**基线证据 |
| 设计新边界 | 当架构发生变化时记录新的组件归属和依赖方向 | **创建或更新** `decision.md` 和架构文档 |
| 拆分重构步骤 | 将重构组织成可回滚的小步骤，每一步结束时系统仍可以构建 | **更新** `task.md` 和 `progress.md` |
| 移动结构 | Generator 只修改内部结构，不混入无关功能开发 | **更新**产品代码和针对性测试 |
| 检测行为漂移 | 对比重构前后的契约、回归、集成、性能和用户旅程 | 运行产品检查；重要不变量使用 `acceptance.json` |
| 评审架构 | Evaluator 检查依赖方向、重复、兼容性以及行为是否真正保持稳定 | 根据需要**使用**审计或端到端评估 |
| 收口 | 架构文档与新结构保持一致，并保存可逆的变更历史 | **更新**长期文档；**归档**变更 |

如果重构过程中必须改变行为，该行为必须成为明确的功能验收项，不能隐藏在重构范围中。

### 场景 E：接入第三方服务

示例：为应用接入支付、身份认证、消息或数据分析服务。

| 阶段 | 工作流如何运行 | 涉及的文件与操作 |
| --- | --- | --- |
| 定义需求 | 固定业务结果、服务商责任、交换的数据、可用性预期和非目标 | **创建** `requirements.md` |
| 比较方案 | 比较供应商成熟度、API 稳定性、成本、许可证、隐私、锁定风险和替代方案 | **创建** `decision.md` |
| 限制访问 | 声明凭据、环境、权限范围、数据等级、外部写入、成本限制和停止条件 | **读取**治理与自治政策；影响较大时**创建** `contract.md` |
| 设计失败行为 | 拆分超时、重试、幂等、限流、降级和数据对账 | **更新** `task.md` |
| 安全实现 | 凭据不进入源代码，适配层隔离供应商特有行为 | **更新**产品代码、配置模板、测试和 `progress.md` |
| 观察交互 | 使用沙箱调用、结构化日志、指标、链路和响应证明成功与失败路径 | **遵循** `docs/OBSERVABILITY.md`；**更新**证据 |
| 独立评估 | Evaluator 测试有效、无效、重复、延迟、不可用和权限拒绝等场景 | **使用** `acceptance.json` 和 `skills/end-to-end-evaluator/` |
| 发布与运行 | 完成 CI、人工评审、回滚或禁用服务商的步骤、Owner 和运行手册 | **使用** Pull Request；**更新**运行文档；**归档**变更 |

只有当第三方服务失败时应用仍然可以预测地处理，集成才算真正完成。

### 场景 F：修改数据库结构或迁移数据

示例：拆分客户姓名字段、回填历史记录，并在迁移期间保持旧客户端可用。

| 阶段 | 工作流如何运行 | 涉及的文件与操作 |
| --- | --- | --- |
| 盘点影响 | 识别 Schema、数据量、消费者、保留要求、敏感字段和兼容窗口 | **读取**架构、Schema 定义、数据政策和近期变更 |
| 定义不变量 | 将预期数量、转换规则、兼容性、完整性约束和回滚边界变成验收标准 | **创建** `requirements.md` 和 `acceptance.json` |
| 选择迁移策略 | 比较扩展—收缩、双写、回填、切换和回滚方案 | **创建** `decision.md` |
| 演练 | 规划备份、代表性数据、Dry Run、耗时、失败注入和恢复步骤 | **创建** `contract.md`；**更新** `task.md` |
| 分阶段执行 | 将 Schema 变更、应用兼容、回填、验证和清理保持为独立检查点 | **更新**迁移文件、产品代码、测试、`task.md` 和 `progress.md` |
| 观察数据状态 | 在不暴露敏感数据的情况下记录数量、拒绝行、延迟、复制和完整性检查 | **遵循** `docs/OBSERVABILITY.md`；**更新**证据 |
| 评估并批准 | Evaluator 在切换批准前重现升级、回滚、旧客户端和部分失败行为 | **使用** `skills/end-to-end-evaluator/`；核对 `acceptance.json` |
| 完成迁移 | 只有兼容窗口结束且证据通过后才进行清理 | **验证** CI 和变更语义；**归档**记录并更新 Schema 文档 |

不可逆的清理步骤必须等待恢复和兼容性证据被正式接受。

### 场景 G：提升性能或降低成本

示例：在不改变用户可见行为的情况下，缩短仪表盘加载时间并降低数据库成本。

| 阶段 | 工作流如何运行 | 涉及的文件与操作 |
| --- | --- | --- |
| 建立基线 | 在优化前测量工作负载、环境、延迟分布、吞吐量、资源使用和成本 | **创建** `requirements.md`；在 `progress.md` **更新**可复现的基线证据 |
| 设置护栏 | 将目标指标、行为、正确性、可靠性和成本约束变成稳定标准 | **创建或更新** `acceptance.json` |
| 找到瓶颈 | 通过性能分析、查询、链路、日志和指标识别主要原因，而不是猜测优化点 | **遵循** `docs/OBSERVABILITY.md`；**更新** `task.md` |
| 选择取舍 | 比较缓存、查询、算法、并发、基础设施和复杂度方案 | 当选择改变架构或运行成本时**创建** `decision.md` |
| 增量优化 | 每次只实施一个可测量变化，并记录当前版本和结果 | **更新**产品代码、基准、测试、`task.md` 和 `progress.md` |
| 保护正确性 | 在运行基准的同时执行功能、边界、可靠性和用户旅程检查 | **验证**产品测试和关键验收项 |
| 独立评估 | Evaluator 使用同一工作负载重测，并确认性能提升不是来自行为削弱或不真实数据 | **使用**独立基准证据和端到端评估 |
| 制度化 | 将性能预算和回归阈值加入持续检查 | **更新**测试、CI、架构或规则；**归档**变更 |

最终结论必须比较同一个工作负载的优化前后结果；孤立的微基准只能作为辅助证据。

### 场景 H：处理生产事故

示例：一次部署完成后，结算错误率立即上升。

| 阶段 | 工作流如何运行 | 涉及的文件与操作 |
| --- | --- | --- |
| 声明事故 | 外化影响、开始时间、受影响旅程、当前 Owner、沟通渠道和即时安全边界 | **创建或更新**事故范围的 `progress.md` 和需求记录 |
| 稳定系统 | Owner 在回滚、关闭功能、降低流量或其他可逆控制中作出选择 | **读取**治理规则和运行手册；在 `decision.md` **记录**选择 |
| 观察现场 | 日志、指标、链路、部署状态和用户可见失败形成共享时间线 | **遵循** `docs/OBSERVABILITY.md`；附加证据但不暴露敏感数据 |
| 限制修复范围 | 将最小 Hotfix 和明确非目标从后续大范围清理中分离 | **更新** `requirements.md`、`task.md` 和停止条件 |
| 实现 | Generator 执行已授权的控制或修复，并保存每个命令和结果 | **更新**产品代码或配置、测试和 `progress.md` |
| 验证恢复 | Evaluator 确认原始旅程、系统健康、负向路径和回滚状态 | **使用** `acceptance.json`、`contract.md` 和 `skills/end-to-end-evaluator/` |
| 安全交付 | 记录审批、CI、部署证据、观察窗口和剩余风险 | **使用** Pull Request 和运行交付记录 |
| 事故后沉淀 | 将根因、促成条件、检测缺口和预防动作转为长期工作 | **归档**事故变更；**更新**测试、规则、Skill、架构或运行手册 |

事故的紧迫性可以缩短反馈周期，但不能取消证据、授权或回滚要求。

### 场景 I：准备并发布一个版本

示例：将通过测试的应用版本从 Staging 发布到 Production。

| 阶段 | 工作流如何运行 | 涉及的文件与操作 |
| --- | --- | --- |
| 选择范围 | 固定包含的变更、排除内容、依赖、迁移、Feature Flag 和 Release Owner | **读取**已完成变更；**创建**发布需求和任务清单 |
| 确认就绪 | 每个包含的变更都拥有最终判定、证据、剩余风险和回滚方式 | **读取** `acceptance.json`、`task.md` 及活动或归档记录 |
| 构建制品 | 从可复现版本生成不可变的软件包、镜像或部署候选 | 在发布证据中**更新**版本和制品身份 |
| 发布演练 | 执行 Staging 用户旅程、迁移、配置、监控、回滚和恢复 | **使用** `contract.md`、可观测性和端到端 Evaluator |
| 正式批准 | Release Owner 审查检查结果、已知风险、发布窗口和人工 Gate | **使用**治理规则、Pull Request 证据和 CI |
| 执行发布 | 由获得授权的交付机制修改目标环境 | 在 `progress.md` **更新**时间、动作和观察状态 |
| 发布后验证 | 在观察窗口检查健康状态、关键用户旅程、指标、日志和错误预算 | **更新**验收状态和最终判定证据 |
| 收口 | 保留 Release Notes、运行状态、回滚状态和后续任务 | **归档**发布记录并更新长期文档 |

## 企业落地路径

建议渐进式采纳：

| 阶段 | 重点 | 进展证据 |
| --- | --- | --- |
| 1. 建立基线 | 入口、红线、变更模板、确定性检查 | 重要工作可见且可以复现 |
| 2. 建立治理 | 风险、Owner、审批、回滚、Skill 责任 | 高风险工作可以追踪 |
| 3. 建立度量 | 质量、周期、成本、返工、例外、评估可靠性 | 决策开始使用趋势数据 |
| 4. 自适应改进 | 动态上下文、工具选择、评估集、知识自动升级 | Harness 变更能改善真实指标 |

不要用提示词数量或生成代码行数评价个人。应衡量系统是否减少缺陷、歧义、返工、不安全操作和恢复成本。

## 项目验证

运行完整检查：

```bash
./scripts/harness-check.sh
```

它会验证必要文件、可疑凭据文件名、语言策略、变更记录语义、文档链接、活动变更新鲜度和检查器测试。

## 当前状态与下一步

当前基线为 `v0.2`。它已经建立 L2 治理所需的控制平面接口，但真正的企业就绪仍需要真实产品项目的采纳证据。

建议下一步选择一个正在开发的仓库进行试点：

- 一个 G1 功能或依赖变更；
- 一个 G2 安全、权限或兼容性变更；
- 一套项目专属可观测性适配器；
- 一段用于衡量返工、缺陷、交付时间和评估可靠性的观察周期。

设计依据可继续阅读 [成熟度模型](docs/MATURITY_MODEL.md) 和 [视频分析文档](docs/knowledge/harness-engineering-video-analysis-bv12lr1b3eut.md)。
