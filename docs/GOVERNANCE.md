# 治理模型

## 决策等级

| 等级 | 示例 | 默认处理 |
| --- | --- | --- |
| G0 可逆、局部 | 文档、测试、非破坏性重构 | AI 可执行并验证 |
| G1 有限影响 | 新依赖、公共接口、小型数据迁移 | 记录理由，至少一名人类审查 |
| G2 高影响 | 权限、安全边界、生产配置、兼容性破坏 | 变更提案、领域负责人批准、回滚演练 |
| G3 不可逆/监管 | 删除生产数据、公开敏感信息、重大合规变化 | 明确授权、双人批准、审计记录 |

风险等级由影响面、可逆性、数据敏感度和外部副作用共同决定；不确定时向上取整。

## 角色

- **Owner**：对规则和最终结果负责。
- **Planner**：澄清需求、风险、约束与验收标准。
- **Generator**：在批准范围内实现，并生成验证证据。
- **Evaluator**：独立检查逻辑、规范、安全与架构影响。
- **Archiver**：归档 Spec、决策、指标和经验。

小团队可以一人承担多个角色，但 G2/G3 的 Generator 与批准者不能是同一个决策主体。

## 规则变更

修改 `rules/`、审计评分或审批边界时：

1. 创建 `changes/<id>/requirements.md`；
2. 说明动机、适用范围、迁移方式和失败模式；
3. 给出兼容性影响及回滚方案；
4. 通过 Pull Request 审查；
5. 合并后记录版本并通知受影响项目。

## 例外管理

规则例外必须包含：

- 具体规则和适用范围；
- 业务理由与风险；
- 补偿控制；
- 负责人；
- 到期时间。

永久、无负责人或无到期时间的例外无效。

## 指标

首批指标只追踪可行动信息：

- 变更具备明确验收标准的比例；
- 自动检查通过率与不稳定检查率；
- AI 变更返工率、回滚率和逃逸缺陷；
- 从提案到合并的周期；
- 规则例外数量与逾期率；
- 人工审查发现的高风险问题类型。

指标用于改善系统，不用于以代码行数或提示词数量评价个人。
